## 0. 结论

1. **资料变多以后，RAG 的回答正确率持平，但检索变差，误拒变多。** R1 vs R0 的回答正确率是 0.887 → 0.863，95% CI [-0.110, +0.063]，判为「持平」。同时，MRR 从 0.950 降到 0.816，Answer Relevancy 从 0.790 降到 0.712，两项都判为「下降」。误拒从每次 1/50 升到每次 4–5/50。逐题看，变差的题大多是 L1 的面试题库挤进了 top-5，把 L0 的笔记挤了出去（第 5.1 节）。
2. **资料少时（L0，86 KB），长上下文比 RAG 好。** LC0 vs R0 的回答正确率是 0.887 → 1.000，95% CI [+0.040, +0.207]，判为「提升」。代价是每题输入 token 是 RAG 的 21.8 倍。按实际缓存命中算，每题费用是 RAG 的 1.6 倍；假设没有缓存，是 15 倍。P95 只多了约 0.07 秒。
3. **资料多时（L0 + L1，1.35 MB），长上下文和 RAG 的差别不显著。** LC1 vs R1 的回答正确率是 0.863 → 0.967，95% CI [-0.007, +0.213]，判为「持平」。CI 的下限很接近 0，所以不能说两者一样好。LC1 每题输入 351,587 token，是 RAG 的 291 倍。每题费用按实际缓存命中是 RAG 的 8.4 倍，假设没有缓存是 215 倍。P95 多了约 1.6 秒。
4. **Haiku 的回答正确率评分可信。** Opus 5.5 给 R1 第 1 次运行评分。Opus 和 3 次 Haiku 的逐题 Spearman 相关系数是 0.945，多数标签一致率是 50/50（第 6 节）。所以回答正确率的结论不用写「仅供参考」。
5. **费用远低于估算。** 12 次正式运行花了 $1.95，加上 smoke 一共 $2.17，上限是 $12。原因是 LC1 完整运行的缓存命中率是 0.999，运行前估算时用的 smoke 命中率只有 0.58。

## 3. 配对比较（第 7.5 节）

判定规则：配对 bootstrap 1000 次，种子 20261102。95% CI 不包含 0，才写「提升」或「下降」；包含 0 就写「持平」。延迟、token 数和费用只报告均值和范围，不做 CI。

## 7. 测量的局限

1. **文档级 Recall@K 有偏差。** `compute_recall_at_k()` 只认题集里的 `source_doc`（L0 的某份笔记）。L1 里有同样正确的内容，检索到它也算没命中。所以 R1 的 Recall@5 和 MRR 偏低。主指标用回答正确率，Context Recall 不看文件名，可以作对照。
2. **题目只考 L0 的内容。** 60 道题都是按 L0 出的。L1 在这个实验里只是「干扰资料」，不是被考的知识。所以本实验测的是「干扰资料变多时 RAG 和长上下文的变化」，不是「在 1.35 MB 的知识上答题」。
3. **并发数和上一个任务不同。** 本任务是 4，上一个任务是 8。延迟不能和上一个任务直接比。
4. **`DocProcessor` 把代码块里的 `#` 注释当成标题。** 这会影响 `heading_path`，本任务没有修改（第 2.2 节）。
5. **费用的时段不一样。** R0 有 2 次运行在非高峰时段，其他运行在高峰时段（第 2 节）。
6. **缓存命中不可控。** DeepSeek 不保证缓存命中。R1 第 1 次的命中率是 0.16，第 2、3 次是 0.84。LC1 的命中率是 0.999，所以按实际缓存命中算的费用倍数（8.4 倍）依赖这个条件。
7. **只有 50 道可回答题。** CI 比较宽。LC1 vs R1 的 CI 是 [-0.007, +0.213]，题再多一些，结论可能变成「提升」。
8. **校准只覆盖 R1 的回答**（第 6 节）。
