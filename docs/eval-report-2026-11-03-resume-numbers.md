# 评测报告：补测（检索方式对照、盲区分类耗时）

- 日期：2026-11-03
- 任务文档：v1.0（内部文档，没有公开）
- 分支：`feat/l1-scale`
- 执行人：施工 Agent D
- L1 的原始结果文件含个人笔记，没有公开；数字来自本地结果文件，统计文件在 `results/stats/`。
- 费用：$0。2 项测量都没有调用 LLM，也没有调用 reranker。

## 0. 结论

1. **M1：混合检索没有比纯向量检索好。** 在 L0 集合上，纯向量的文档级 Recall@5 是 0.980，混合检索是 0.960。MRR 是 0.932 对 0.950。2 个差值的 95% CI 都包含 0，判为「持平」。所以「混合检索把 Recall@5 从纯向量的水平提高到 0.96」这个说法没有数据支持。
2. M1 里唯一判为「提升」的比较是 L0 上混合检索对纯 BM25 的 MRR：0.905 → 0.950，差值 +0.045，95% CI [+0.010, +0.095]。
3. **M2：** 现在的 L0 知识库有 471 个主题（不是 2026-04 的 259 个）。分类这一步 P50 是 6.0 ms，P95 是 6.4 ms（默认配置）。这个耗时不包括 LLM 写报告。
4. 主题数到 1326 个（L1 数据库）时，P50 是 15.5 ms。但 50 次里有 4 次碰上 Python 的全量垃圾回收，每次多 140–150 ms，所以 P95 是 158 ms。

## 1. M1：检索方式对照

### 1.1 做法

- 脚本：`backend/evaluation/retrieval_ablation.py`（commit `8617614`）。单元测试：`backend/tests/test_retrieval_ablation.py`。
- 题目：`qa_l0_v1.json` 里的 50 道可回答题。题集 SHA-256（按 LF 换行计算，和 `eval_rag.py` 一样）：`ee47c4ec…f6c2d0db`。
- 3 种方式。每种方式都从 Milvus 取 15 条，再保留前 5 条。这和 `rag_search` 在 `ENABLE_RERANKER=false` 时的做法一样：

  | 方式 | 调用 | 说明 |
  |---|---|---|
  | `dense` | `milvus_service.search()` | 只用 BGE-M3 向量，HNSW ef=128 |
  | `bm25` | `milvus_service.bm25_search()` | 只用 BM25，k1=1.2，b=0.75 |
  | `hybrid` | `milvus_service.hybrid_search()` | 向量 + BM25，RRF k=60 |

- 2 个集合各跑 1 次。检索结果是确定的，所以不重复跑。
- 配对 bootstrap 用 `stats.py` 的 `paired_compare()`：1000 次，种子 20261102。差值 = `hybrid` 减另一种方式。CI 不包含 0 才判为「提升」或「下降」，否则是「持平」。

### 1.2 指标定义

- **文档级**（直接用 `eval_rag.py` 的 `compute_recall_at_k()` 和 `compute_reciprocal_rank()`）：
  - Recall@5：前 5 条里有题目的 `source_doc`，记 1，否则记 0。
  - MRR：第 1 条来自 `source_doc` 的结果排第几，取倒数；没有就是 0。
- **章节级**（`eval_rag.py` 里没有现成的函数，脚本里新写）：
  - 先定义「一条结果属于金标章节」：结果的 `source_doc` 和金标相同，并且 `heading_path` 等于金标的 `heading_path`，或者是它的下级标题（以「金标路径 + `/`」开头）。
  - 章节 Recall@5：题目的金标章节里，有几个被前 5 条中至少 1 条覆盖，除以金标章节数。50 道题里 49 道有 1 个金标章节，1 道有 2 个。
  - 章节 MRR：第 1 条属于任一金标章节的结果排第几，取倒数。
  - 章节 Hit@1：第 1 条结果属于任一金标章节，记 1，否则记 0。

### 1.3 自检（任务文档第 1.2 节）：通过

| 集合 | 要求（R0 / R1） | `hybrid` 实测 | 和 R0 / R1 的前 5 条 chunk id 对比 |
|---|---|---|---|
| `secondbrain_docs`（187 行，4 份文档） | Recall@5 0.960，MRR 0.950 | 0.960，0.950 | 50 / 50 道题完全相同（`rag_eval_20261102_215402.json`） |
| `secondbrain_l1`（1935 行，48 份文档） | Recall@5 0.880，MRR 0.816 | 0.880，0.816 | 50 / 50 道题完全相同（`rag_eval_20261102_220755.json`，没有公开） |

注意：R0 的 MRR 0.950 来自「先取 15 条，再截前 5 条」。如果直接调用 `hybrid_search(top_k=5)`，向量和 BM25 两路在融合前各只取 5 条，MRR 是 0.921（R0 结果文件里的 `rr_raw`）。以后引用 0.95 时，口径是前一种。

### 1.6 差别来自哪些题

- 3 种方式的差别几乎都在 10 道改写题（`paraphrase`）上。其他 40 道题在 L0 上 3 种方式的 Recall@5 和 MRR 都是 1.0。

### 1.7 范围

## 2. M2：盲区分类耗时

### 2.1 做法

- 脚本：`backend/evaluation/time_gap_classify.py`（commit `c279709`）。单元测试：`backend/tests/test_time_gap_classify.py`。
- 用 `eval_agent.py` 的 `_setup_mastery()` 给测试用户 `timing_gap_user` 写 mastery 记录，预设 `__half_weak__`：主题按名字排序，前一半 0.8 分，后一半 0.15 分。
- 每组先调用 1 次 `_classify_topics()` 预热，再连续调用 50 次。每次调用用一个新的 `AsyncSession`，和一次请求一样。计时用 `time.perf_counter()`，只包住 `_classify_topics()`。
- 计时范围：`search_concepts`（读全部主题）、`read_mastery`（读这个用户的全部记录，算时间衰减）、Python 分类规则。**不包括 LLM 写报告。**
- 每组测 2 次：
  - `echo_on`：按现在的默认配置。`APP_ENV` 默认是 `development`，`app/db/database.py` 会打开 SQLAlchemy 的 SQL 日志（echo）。
  - `echo_off`：只在测量进程里把 `engine.echo` 设为 False。没有改 `app/` 下的代码。
- 第 1 轮测量发现，慢的调用都碰上了 Python 的第 2 代（全量）垃圾回收。所以脚本在第 2 个 commit `c279709` 里加了记录：用 `gc.callbacks` 记下每次调用里全量回收用了多少毫秒。垃圾回收保持打开，和后端一样。下表同时给出「全部 50 次」和「去掉碰上全量回收的调用」两种统计。第 1 轮（commit `8617614`）的结果文件已删除，数字和第 2 轮一致。

分类结果（每组相同）：471 个主题是「薄弱盲区」236、「已掌握」235；216 个主题是 108、108；1326 个主题是 663、663。「未接触盲区」和「需巩固」都是 0，这符合 `__half_weak__` 预设。

### 2.4 怎么读这些数字

- **P50 是分类这一步本身的耗时。** 471 个主题约 6 ms，216 个主题约 3.5 ms，1326 个主题约 15.5 ms，大致和主题数成正比。
- **P95 和最大值受全量垃圾回收影响。** 每次全量回收用 140–150 ms。它要检查整个测量进程里的全部对象（约 64.4 万个，包括导入的库），所以耗时和分类本身无关。主题越多，每次调用分配的对象越多，全量回收就越常碰上。1326 个主题时，50 次里碰上 4 次，所以 P95 落在回收上。
- 后端进程里的对象数量和测量进程不一样，所以全量回收的频率和耗时也会不一样。1326 个主题的 P95 不能代表后端的实际耗时。
- SQL echo 关闭后，P50 少约 0.3 ms。
- 第 1 轮测量里，`scope=RAG复习.md` 的 echo_off 组碰上过 1 次回收（97 ms），第 2 轮没碰上。碰不碰上取决于进程累计分配了多少对象，不固定。

### 2.5 测试用户已删除
